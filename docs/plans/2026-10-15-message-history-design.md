# 聊天历史与连续阅读优化

2026-10-15。继续优化现有工作台，仅修改源码和开发构建，不执行桌面打包。原工作区数据和官方 CLI 配置不参与测试。

## 已确认的问题

- 聊天接口最多返回最近 100 条，界面没有更早记录的入口。
- 每次刷新替换这 100 条，持续来消息时会移除用户正在看的旧记录。
- 读取一个房间会反序列化全部房间的消息，并逐条读取相关任务。

## 方案与范围

采用按消息写入顺序的游标分页。首屏读取最近 100 条，用户点击“加载更早消息”读取上一页；刷新从已读到的最新游标向后补齐。加载过的页在本窗口的房间缓存中保留。旧的数组接口继续兼容。

一次返回全部记录虽然简单，但会增加首屏和持续刷新的成本；只扩大原有 100 条上限仍无法访问更久的记录。完整列表虚拟化留待真实数据量证明有需要时处理，本轮优先解决可访问性和数据连续性。

SQLite 按房间建立消息索引，并在数据库中完成归档过滤及分页。游标绑定房间，不依赖时间戳，避免同一毫秒和时钟变化导致漏项。每页提供归档可见范围标识；范围变化时重新读取已经展开的历史区间，避免恢复或归档后残留旧显示。

界面的消息读取从 App 抽出，按工作区及房间管理状态。每个房间串行读取，合并刷新请求；迟到响应只更新自己的房间。加载失败保留已读内容，历史加载与最新消息刷新分别提示、分别重试。历史页插入以可见消息及其偏移恢复位置，不增加未读计数。

## 验证

1. 服务与 HTTP：跨页顺序、同时间戳、无重复无缺失、房间隔离、非法游标、归档过滤、旧数据库索引及旧接口兼容。
2. 消息状态：长时间断线补齐、刷新合并、翻页失败重试、切换隔离、归档及恢复、同一消息去重。
3. 真实 Electron：超过 200 条历史的翻页、阅读位置、未读提示、请求失败与迟到、房间往返及小窗口。保留截图和检查回执。
4. 最终运行 npm test、npm run check、npm run build，并记录结果及未执行的检查。核对现有发布入口哈希不变。

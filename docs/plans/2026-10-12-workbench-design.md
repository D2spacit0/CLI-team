# CLI Team 聊天协作工作台设计规划

版本：2026-10-12，供实施与评审。本文是前端设计交付，不代表功能已实现。

**产品目标：用户在一个聊天室交代目标、指定团队、看见成员接力，遇到问题就地处理，最后根据成果和验证作出验收。**

推荐重构前端应用壳层，后端逐项补齐原生会话和消息路由。保留现有任务调度、材料准备、草稿、独立评审与局部恢复。依据见[源码研究](../research/2026-10-12-ccgui-multi-cli-studio.md)，字段及接口见[运行与房间合同](2026-10-12-runtime-room-contract.md)。Gemini 从[前端任务书](2026-10-12-gemini-frontend-brief.md)开始。

## 1. 用户心智与术语

| 用户看到的对象 | 用途 | 与其他对象的关系 |
| --- | --- | --- |
| 工作区 | 当前项目和保存位置 | 对应一个本地服务数据范围；切换由桌面桥完成 |
| 聊天室 | 某个持续话题的讨论与协作记录 | 可以关联任务；可见聊天记录不等于任何 CLI 的完整原生上下文 |
| 成员 | 一个配置好的 CLI 执行身份 | 同一种 CLI 可以配置多个成员；技能是用户描述，不能证明能力 |
| 会话 | 某成员在某个上下文中的连续对话 | 原生会话 ID 由客户端产生；换聊天室/任务/执行角色不能串用 |
| 任务 | 有目标、分工、交付标准与验收的工作 | 在聊天室内查看和操作；聊天答复不自动推进任务 |
| 执行记录 | 一次实际排队或启动的工作 | 对应具体成员、阶段、结果和日志 |
| 成果 | 实际文件或结构化分析结果 | 关联产出步骤和版本；可以打开对应验证 |
| 需要我处理 | 当前必须用户处理的问题集合 | 求助、权限、失败、待验收；历史失败不重复充当当前告警 |

统一界面用“聊天室”“负责人”“协作者”“独立评审”“待验收”“执行记录”。服务现有的 room、assigneeId、review 等字段由映射层解释，不直接作为产品文案。

### 房间的三种使用方式

1. **单聊**：与一个成员连续交流；只切换查看对象不启动执行。
2. **团队讨论**：向明确的人提问，或发起一轮有边界的多人讨论。
3. **协作任务**：负责人制定计划，协作者依次交付，负责人整合，机器检查与独立评审，用户验收。

这些方式共用工作台布局。单聊/成员名单是新增房间能力；第一阶段面对旧后端时只呈现已有聊天室、显式收件人与任务，不伪造单聊会话绑定。

## 2. 信息架构

主导航只保留四个高频入口，另将设置放在底部。

| 一级入口 | 列表内容 | 主区 |
| --- | --- | --- |
| 聊天室 | 最近房间、搜索、置顶、归档入口 | 当前话题的连续时间线与输入框 |
| 任务 | 待准备、进行中、需要处理、待验收、已完成；支持列表/看板 | 选中任务的上下文、计划、成果与动作 |
| 成员 | 名称、CLI、能力状态、负载 | 成员配置、连接诊断、关联执行记录 |
| 需要我处理 | 当前问题，按阻塞程度与时间排列 | 原问题及必要上下文，直接进入操作 |
| 设置 | 工作区、运行调度、桌面偏好 | 代理/并发等现有设置与高级诊断 |

成果跟随任务与聊天室，不再要求用户先跳到全局成果页找文件。全局成果检索保留在任务入口。外部 DSH 会话放到成员/会话的“外部会话”页签；继续保持观察和导入资料的语义。

“搜索”“置顶”“未读”“全局待处理”若未获得后端支持，第一阶段只提供明确标注范围的本地筛选或暂不出现；不能把最近 50 次运行筛选结果称为全量搜索。

### 页面地址建议

使用同源 hash 路由，避免桌面刷新依赖新服务器路由；路由实现可以很小，无需为此立即增加库。

```text
#/rooms/:roomId
#/rooms/:roomId?task=:taskId&panel=plan|members|materials|artifacts
#/tasks?filter=attention
#/tasks/:taskId
#/members/:memberId
#/attention
#/settings
```

任务、房间、面板和返回位置可恢复；进行中操作与授权勾选不可从 URL 恢复。旧 `?room=` 链接在启动时兼容转为新地址。

线框中的成员、文件和状态是设计场景示例，不预置到用户数据中。

主区始终保留聊天上下文。右栏一次显示一个检查对象；“查看成果”和“查看日志”改变检查对象，不关闭任务、不清空输入。长内容需要展开到主区时，提供明确返回按钮。

### 3.2 “成员接力”是核心识别元素

聊天室标题下面保留一条紧凑的成员接力条，来自实际任务步骤与运行状态：

`负责人 正在规划 → 接口成员 已交付 → 页面成员 等待接口答复 → 独立评审 未开始`

- 箭头只在存在依赖/交接时出现，不把参与者名单画成虚构流程。
- 点击成员定位相关消息及执行记录；点击“等待答复”定位当前问题。
- 显示当前任务或当前讨论的范围；同一房间多个任务时先选择任务。
- 无步骤计划时显示“尚未形成执行计划”，不生成假进度。
- 数字使用“已交付 2 / 3 步”，不估算“完成 67%”。结构检查缺失的旧步骤不进入“已验证交付”计数。

### 3.3 窗口与缩放

| 可用 CSS 宽度 | 布局规则 |
| --- | --- |
| ≥1440 | 导航 48，房间列表 216，主区伸展，右栏 360 |
| 1280–1439 | 导航 48，列表 208，右栏 320；主区至少 560 |
| 1040–1279 | 导航 48，列表 192；右栏默认抽屉，打开不挤压输入框 |
| <1040，含高缩放场景 | 列表收为抽屉；主区单列；任务/成果作为可返回的详情视图 |

窗口整体不横向滚动。代码、表格和 diff 可在各自容器内横向滚动。所有栅格子项 `min-width:0`，纵向容器 `min-height:0`。标题、可滚动正文、底部动作分层；高度不足时输入框最多占可用主区的 35%。

按现有桌面最小窗口 1040×700 回归，并覆盖 Windows 100% / 125% / 150% 缩放，不把“窗口够大”当成可用性前提。

## 4. 核心交互

### 4.1 首次使用与成员接入

1. 打开后恢复当前工作区和上次房间；没有记录时显示“添加成员，开始讨论”。
2. “检测本机客户端”调用已有 discover。只显示检测到可执行入口，不据此显示“已登录”。
3. 添加成员填写名称、CLI、职责、擅长内容；高级区提供模型、路径、参数数组和运行策略。
4. 新能力接口上线后才出现“检查连接”，显示版本、能力、检查时间与失败原因。
5. 登录操作指向官方客户端；本产品不要求复制客户端凭据。

成员卡固定显示四组信息：身份、技能描述、连接状态、负载。忙碌成员可选且会排队；缺失或停用成员不可派工。颜色与文本同时说明原因。

权限文案描述实际保证，例如“仅分析”“允许工作目录内编辑”；详细区说明该 CLI 的限制由运行时执行还是仅提示词约束。未验证的能力显示“未验证”，不显示绿色可用。

### 4.2 新建聊天室

最终表单：名称、使用方式、成员、可选负责人。单聊要求 1 名成员；团队讨论与协作房间要求明确成员列表。房间可复用成员配置，不复制凭据或原生会话。

旧接口阶段：只提交 `name` 创建房间，保留每条消息的明确收件人。成员绑定、默认负责人、改名等依赖新增接口，暂不提供保存成功的假反馈。

### 4.3 发送消息

输入区由“收件范围”“文字”“附件”“发送动作”四部分组成。

- 收件人使用可移除的成员标签；键入 @ 打开候选菜单。候选包含职责、CLI、忙碌状态和禁选原因。
- 在发送按钮上方显示“发给张工、设计成员 · 关联：首页交付”，用户不需要猜测消息会触发谁。
- 单聊默认发给绑定成员；团队房间只有已明确配置的负责人可作为默认收件人。
- 旧接口中没有收件人时按钮叫“记录消息”，并显示“仅保存到聊天室”；指定收件人后叫“发送消息”。
- 多收件人一次形成一个用户消息、多个独立投递结果。部分失败逐项显示，不删除成功部分。
- `Enter` 发送、`Shift+Enter` 换行；中文输入法 composition 期间 Enter 只确认输入。
- 发送失败保留文本、附件引用和目标；不自动重发可能已启动的请求。
- 聊天室切换保留各自草稿；该能力需要新增 room-message 草稿 scope，不能误用 new-task scope。

**旧后端的 @ 兼容说明：** 当前会扫描正文里的 `@handle` 并与 recipientIds 合并，包括粘贴的文字。第一阶段发送预览必须体现这个实际集合。新接口改用经过校验的结构化 mention 引用；引用代码中的 @ 不自行派工。两种语义必须按合同版本区分。

“只用当前消息分析”对应现有 `analysisOnly:true`，表示不使用工具，不可泛化成所有“只读”场景。任务内普通咨询已有只读约束；咨询答复不推进任务、不替换验收。

### 4.4 执行中与待发消息

- 切换成员视图不会打断当前执行。
- 新消息如果加入队列，必须显示实际收件人、排队原因、是否等待当前任务结束。
- “取消待发”只撤回尚未提交的投递；“停止当前执行”作用于确定的 run。
- 第一阶段沿用后端既有排队，不做前端持久待发重放。新版投递接口落地后再增加逐条编辑/撤回。
- 成员无增量输出时显示“运行中，尚未收到正文”；断连时显示“连接中断，当前状态待同步”。均不合成打字动画或完成百分比。
- 用户往上读历史时，不自动拉回底部；底部出现“有新消息，返回最新”。流式块更新不使页面抖动。

### 4.5 发起多人讨论

入口：聊天室标题菜单中的“发起讨论”。填写议题并选择 2–4 名可用成员。提交前说明流程：“先分别给出意见，再互相质疑，最后由首位成员汇总”。

讨论结果分为建议、分歧、待补证据。用户可以“据此创建任务”，将建议作为准备表单的背景；保留原讨论来源，仍需明确目标、团队和完成标准。讨论完成不自动执行建议。

某阶段失败时展示失败成员与原因，保留其他意见。现有服务没有讨论暂停/恢复 API，因此第一阶段不提供这类按钮；可按已有 run 取消能力停止具体运行，并同步真实状态。

### 4.6 从聊天室创建任务

“新建任务”在主区或宽侧面板打开准备表单，分区如下：

1. **目标**：标题、详细要求、关联聊天室。
2. **团队**：单人执行 / 负责人协作；负责人、1–4 名协作者、可选独立评审者。
3. **材料**：已选、上传中、已导入、失败、重启后待重选。
4. **完成标准**：自然语言条目；可选机器检查程序和参数。
5. **操作**：“保存待办”“准备完成并开始”。

继续复用现有 TaskCreateDialog 的准备控制逻辑、taskDrafts、TaskInputPicker、TaskTeamFields。拆成新的外观组件时不改变幂等 ID、材料 hash 核验和启动顺序。

必须保留的行为：

- 创建幂等标识先存草稿，再提交任务。响应丢失后恢复同一待办。
- 材料全部成功并核对后才能开始；单份失败只重试该份。
- 关闭或查看成员配置后可回来继续填写；正在保存、已保存、保存失败分别可见。
- 待办创建后的固定字段按现有服务约束展示，不出现可编辑但保存不了的目标/团队。
- 首次运行后材料锁定；重启后的未导入文件要求重新选择。
- 负责人、协作者、评审者按现有规则互斥；任意房间成员身份都不扩张任务授权名单。
- 参数使用“程序 + 每行一个参数”，高级区可查看数组；不提供拼接 shell 字符串的快捷执行。

### 4.7 任务执行与成员求助

右栏“计划”按依赖顺序展示每步的成员、预期交付、当前状态、实际交付和检查结果。当前实现顺序派发步骤，UI 按事实显示。

求助出现于原步骤旁，并在聊天时间线生成同一问题的引用卡：

`页面成员需要接口的错误码 → 负责人咨询接口成员 → 负责人给出答复 → 页面成员继续原步骤`

这是同一个 helpId 的生命周期，不复制成多个独立待办。

- 负责人正在咨询同伴：显示“团队正在处理”，不要求用户抢答。
- 确需人工答复：显示完整问题、已知背景、当前受阻步骤和输入区。
- 保存答复后显示“答复已保存，等待继续”。保存成功不表示已经恢复执行。
- “继续任务”附近显示保留步骤数量与重新执行原因；第一阶段只能用 progress.resume 已有的聚合信息。
- 详细“保留哪些步骤 / 重做哪些步骤”要等恢复预览接口上线，不能前端推测。
- 查看负责人处理日志、咨询来源和原步骤日志，返回后保留答复草稿与位置。

### 4.8 原生权限与用户问题

以下卡片不可混用：

| 卡片 | 谁产生 | 处理后发生什么 |
| --- | --- | --- |
| 业务求助 | 当前任务协作者及负责人调度 | 保存答案，再按任务恢复规则继续 |
| 原生用户问题 | CLI 的结构化用户输入请求 | 将有限答案回送当前运行 |
| 原生工具权限 | CLI 的具体工具审批请求 | 允许本次或拒绝，后端回送到同一原生请求 |
| 计划审批 | CLI 完整计划及其版本 | 按原生能力原地继续或创建后续执行轮次 |

现有后端只具备第一类产品流程。其他卡片第一阶段仅可在明确标注的开发场景中演示，生产中不能出现可点的假审批。

有效权限卡显示成员、任务、请求动作、目标路径/资源、范围和当前版本。运行结束、请求被替代或过期后按钮禁用，显示原因。没有对应原生能力时显示“当前接入不支持界内答复”及诊断入口，不自动改用宽权限模式。

### 4.9 暂停、停止、改派、继续

| 操作 | 影响 | 界面反馈 |
| --- | --- | --- |
| 暂停任务 | 停止当前及后续任务派工，保留已有成果 | 先显示“正在停止”，停稳后显示“已暂停” |
| 停止本次执行 | 取消对应 run；任务如何变化由服务决定 | 保留部分正文与原因；不能宣称已回滚文件 |
| 改派 | 在停稳且服务允许时变更负责人/成员 | 显示现有成果与新分工，保留变更记录 |
| 继续任务 | 服务核对有效交付和依赖，决定复用与重跑 | 从权威状态显示实际继续阶段 |
| 全局暂停调度 | 暂停后续调度 | 设置中说明影响；不能与任务暂停互换 |

动作不叠加常规确认弹窗。取消整个任务、重置原生会话等有特殊后果的操作使用现有明确确认。后端返回 409 时保留表单并刷新事实，不将其当作保存成功。

### 4.10 验收与成果

“待验收”进入成果优先的详情：左侧文件/分析交付列表，主区安全预览，右侧完成标准和证据，底部“提出修改”“接受当前结果”。

```text
┌──────────────────┬────────────────────────────────┬────────────────────────┐
```

- 文件显示相对路径，避免同名混淆；预览不执行 HTML 或交付脚本。
- 现有预览支持什么格式就展示什么；不支持的类型提供现有下载入口。代码预览、diff 和任意文件打开需要补后端能力。
- 并列显示“成员总结”“交付结构检查”“机器检查”“独立评审”“用户决定”，每项可追到相应记录。
- 机器检查未配置、正在执行、失败、已失效，均保持真实状态。
- 用户可在现有允许范围内明确接受没有自动检查的任务；其勾选不随草稿持久化。
- 产物版本变化后，旧证据与旧意见标记失效；服务仍是能否接受的最终判断来源。
- 修改反馈先使用现有字符串接口；带文件、行号、hash 的结构化反馈是后续能力。

### 4.11 需要我处理

每条项目显示：任务/房间、必须用户处理的原因、等待时间、一个主动作。

排序建议：有效权限或问题 → 当前阻塞 → 待验收 → 用户主动暂停。已读不等于解决；查看记录不改变任务状态。全局列表需要专用查询，不能调用只有主控可访问的 `/api/control/inbox`。

第一阶段可以从已加载任务及其 progress 建立“已加载任务的待处理”，明确查询范围和加载状态。不得只因 bootstrap 的近期 runs 缺少某记录就判定该任务空闲。

## 5. 消息组件与显示来源

| 类型 | 主体信息 | 可用动作 | 来源要求 |
| --- | --- | --- | --- |
| 用户消息 | 正文、收件人、关联任务、发送状态 | 复制、引用、查看投递 | 持久 message；乐观占位明确标记未发送 |
| 成员正文 | 成员、CLI、正文、部分/完整标记 | 复制、查看本次执行 | 原生正文事件或已保存 summary |
| 工具活动 | 工具名、目标、当前状态、输出摘要 | 展开详情 | 归一化工具事件，按 toolCallId 关联 |
| 派工计划 | 负责人、计划版本、步骤数量 | 查看计划 | 经服务校验的计划；模型草稿单独标明 |
| 成员交接 | 发起人、接收人、问题/交付、关联步骤 | 定位上下游 | 路由或求助事实，不从普通正文猜测 |
| 交付卡 | 相对路径/分析章节、版本、结构检查 | 查看成果和检查 | artifact / outputCheck |
| 业务求助 | 提问、处理人、答案、状态 | 答复、查看来源、继续 | assistance + 当前任务状态 |
| 权限/问题卡 | 具体请求与有效性 | 仅后端允许的响应动作 | 新原生请求合同 |
| 验证卡 | 检查项、结果、缺失/跳过项 | 查看证据 | 机器记录，不能由模型自述创建 |
| 系统事件 | 暂停、改派、恢复、归档 | 定位相关记录 | 服务事件 |

普通 Markdown 渲染禁止原始 HTML。命令与路径只作为文本/受控链接；成员输出中的“运行此命令”不会生成自动执行按钮。未知事件类型保留诊断入口，不导致整个聊天室崩溃。

## 6. 状态规则

### 三层状态分别显示

1. **连接/会话**：未检测、可用、连接中、已断开、会话失效、能力未知。
2. **执行/投递**：待排队、排队中、运行中、等待输入、正在停止、执行结束、失败、已取消、已中断。
3. **任务/验收**：待准备、执行中、受阻、待验收、已完成、已取消。

“CLI 退出成功”只能更新执行事实。只有服务确认任务 accepted，才显示“已完成”。相同时间线里的任务与单次运行可能具有不同状态。

| 场景 | 文案示例 | 后续动作 |
| --- | --- | --- |
| 原生进程已启动但无正文 | “正在运行，尚未收到正文” | 可停止、查看诊断 |
| CLI 有正文但缺少完成回执 | “保留了部分结果，完成状态未确认” | 查看输出，按服务提供的恢复路径处理 |
| 成员说完成，但交付缺失 | “成员已返回，交付检查未通过” | 查看缺失文件/章节 |
| 服务失联 | “连接中断，显示上次同步结果” | 保留草稿、自动重连、手动重试 |
| 当前任务已恢复，历史有失败 | “当前正在执行” | 历史失败留在记录中 |
| 无自动检查 | “未配置机器检查” | 人工验收入口遵守既有确认规则 |
| 动作已被其他窗口改变 | “状态已更新，请查看当前任务” | 刷新，不清空用户输入 |

## 7. 视觉规范

采用浅色工具工作台：连续消息是阅读主轴，成员接力条与右侧检查区形成任务感。页面顶端直接显示项目和正在做的工作，避免欢迎海报、大统计卡和营销语。

### 色彩与排版

| Token | 值 | 用途 |
| --- | --- | --- |
| background | `#F3F6FA` | 应用背景 |
| surface | `#FFFFFF` | 阅读与表单区域 |
| text | `#172B4D` | 正文、标题 |
| muted | `#53657D` | 时间、次级说明 |
| border | `#DCE4EE` | 分区、控件边界 |
| accent | `#2862D7` | 当前选择和主要动作 |

状态色另设：成功 `#1B7A55`、等待 `#9B6500`、失败 `#BF3D3D`；都同时带文字或图标。状态底色采用低饱和浅底，正文保持足够对比。不能仅用模型品牌色表示成功或失败。

- 中文正文：`"Microsoft YaHei UI", "PingFang SC", system-ui, sans-serif`，14px，行高 1.65。
- 标题：同系统中文字体 18px / 600；房间标题 16px / 600，避免大号展示字。
- 执行 ID、路径、时间与代码：`"Cascadia Code", Consolas, monospace`，12–13px，数字等宽。
- 间距采用 4 / 8 / 12 / 16 / 24；输入区域 padding 12–16；卡片圆角 8，普通控件 6。
- 常规按钮至少 32px 高，关键输入和动作 36–40px；图标按钮有名称、提示和可见焦点。
- 阴影仅用于浮层、拖动中的面板与抽屉；普通消息用间距和细分隔组织。

首期完成浅色主题，使用语义 token 保留后续暗色能力，不为主题切换延迟核心协作。图标复用现有 lucide-react，不新增外网字体依赖。

### 运动与可访问性

面板过渡 120–160ms；尊重 prefers-reduced-motion。流式文本不逐字弹跳。状态更新用适度 aria-live，不朗读每个 token。Tab 可到达所有动作，Escape 关闭浮层并恢复焦点；关闭面板不等于放弃草稿。所有错误信息能用键盘定位。

## 8. 前端实现边界

建议新增模块，按页面与领域组织，避免继续扩大 App.tsx。

```text
ui/workbench/
  WorkbenchApp.tsx
  navigation/           路由、导航、房间列表
  rooms/                房间页、输入框、收件人、时间线
  messages/             正文、工具、交付、求助、验证卡
  tasks/                任务页、计划、准备、验收布局
  members/              成员列表、能力与会话详情
  attention/            待处理列表及范围提示
  inspector/            右侧检查区、执行记录抽屉
  api/                  legacy 与 v2 映射、能力判断
  state/                服务状态缓存、UI 选择、事件归并
  fixtures/             显式演示数据；生产入口不可默认使用
  tokens.css
  workbench.css
```

现有 TaskCreateDialog、taskDrafts、TaskTeamFields、memberAvailability、TaskMaterials、TaskAssistance、TaskAssignment、TaskCoordination、ArtifactPreview、RunDiagnostics 的逻辑优先复用。外观逐项拆分，保留其错误和恢复处理。

服务状态、界面选择、未提交草稿分开存放。可以用 React reducer + 选择器完成第一阶段；出现明确需求再评估额外状态库。避免每个流式事件重取整个 bootstrap，也避免所有卡片都监听同一个大对象。

所有 HTTP 调用经过 api 适配层。新前端不读取 SQLite、不在浏览器启动进程、不访问凭据、不直接执行 Tauri 的 invoke。

## 9. 分批实施与可交付条件

### A. 工作台骨架与已有能力迁移

交付房间/任务列表、连续消息、收件人、固定输入区、任务检查面板、日志往返、新建准备和验收布局。连接现有 API；未知功能不开放。

验收：已有任务数据正常读取；创建准备、材料失败重试、求助答复、暂停改派继续、成果预览和验收保持原行为。1040×700 下主操作可见。演示场景与实际工作区明确隔离。

### B. 原生运行能力与可靠事件

后端先提供能力、运行快照、正文/工具事件、有限原生问题接口。前端增量归并、断线恢复、原生会话详情、有效请求卡。

验收：真实客户端连续两轮；正文可流式出现；同名工具不串；停止后不继续显示运行；断线重连无重复文本；未支持能力显示原因。

### C. 团队聊天室与可追踪交接

接入房间成员、默认负责人、结构化 mentions、replyTo、逐收件人投递状态、上下文清单和可撤回待发消息。将当前 handoff 和 task assistance 投影为接力事件。

验收：前端成员向负责人询问接口，负责人咨询后端成员并回传，原步骤恢复；另一任务的上下文不会混入；引用中的 @ 不误派工；重连不重复投递。

### D. 完整验收与长历史

接入消息分页、全局待处理、恢复范围预览、更多安全文件预览和版本绑定反馈。真实 CLI 协作验收通过后再考虑隔离工作区中的并行写入。

验收：旧任务可继续操作；历史过滤说明准确；机器证据变旧立即禁用接受；未配置/未执行的检查始终可见。

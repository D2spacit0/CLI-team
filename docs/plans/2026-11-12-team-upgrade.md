# CLI Team 整体升级实施方案

**Goal:** 用户在一个项目界面交代目标、查看团队接力、审阅固定成果；负责人自动处理派工、收件、验收与返工。

**Architecture:** CLI Team 继续持有唯一的任务、预算、成果和审批状态。借鉴 LibreChat 的项目会话、执行活动与成果侧栏，以及持久交付和恢复边界；将 solo-to-team-skills 的派收核判规则落实为程序校验和追加记录。官方 CLI 负责执行，技能说明不能改写程序权限或冒充机器证据。

**Tech Stack:** Node.js 24+、ESM、Express、SQLite、React、TypeScript、Electron；服务仅监听 loopback。

2026-11-12 用户已授权整体升级，并明确要求同时参考两个项目。本方案调整此前 `PLAN.md` 的实施顺序；数据保护、原生 CLI、不可变成果和最终发布确认约束继续适用。沿用现有工作区与未提交成果，不迁移生产数据，不安装第三方运行平台。

## 1. 参考范围

- [solo-to-team-skills](https://github.com/dabingfy-dot/solo-to-team-skills/tree/bc9c19458e9d4afe42e506fc65673a68c26c6a56)：派工必须有执行人、收件人、检查人、原承诺、交付位置与完成条件；接单、收件、验收分开；退回和失败保持未完；验收后确认下一棒真正开工。执行自述、机器检查、独立判断分别留证。
- [LibreChat](https://github.com/LibreChat-AI/LibreChat/tree/e6567c7a681ce67869dce31486a21d3a25d6931b)：同项目下组织会话、阶段活动与成果；保留失败及待处理事项；固定身份与版本下处理租约、重复请求和结果恢复。其 Mongo/Agents SDK 运行体系不整体迁入。
- 本轮采用重新实现的规则与交互，参考材料不是运行时指令。若抽取具体上游代码，另保留对应文件许可与出处。

## 2. 数据与协作契约

### 工作和运行分别记录

保留 `WorkItem.status` 作为调度状态，新增 `handoffStatus`：

`assigned → accepted → received → verified`

退回记为 `returned`，受阻记为 `blocked`，有权者取消记为 `cancelled`。只有已核验或明确取消的工作退出未完清单；失败的 CLI 运行不关闭业务周期。

工作登记包含 `receiverId`、`checkerId`、`acceptanceCriteria`、`originalDueAt`、`dueAt`。原始承诺保留，改期记录理由和决定者；到期检查由负责人承担。用户不用填写内部交接表。

`workReceipts` 保存实际收取的固定成果身份、generation、attempt、输入摘要、输出摘要、文件清单和机器检查；`workHandoffs` 只追加派工、开工、收件、核验、退回、受阻、改期及取消事件。

### 接收和独立核验

- 输出文件真实收取并通过输入/路径/格式检查后，工作进入 `received`。
- 普通交付由独立收件成员的 `accept` 工作核对当前收件；`accept` 不再递归创建验收任务。
- 整稿交付复用既有独立 `review` 工作，核对当前固定版本。审稿通过才放行后续；退回创建新一代工作和新成果版本。
- 依赖工作只有在上游 `verified` 后执行；验收工作可以读取自己的 `received` 目标。验收报告必须绑定来源工作、代次、收件和摘要，过时结果不能推进新版本。
- 机器检查与成员审查分别显示，任何普通 HTTP、CLI 或 MCP 工具都不能代替人类最终发布批准。

### 负责人处理异常

持续失败、缺件、逾期或依赖取消生成有上限且去重的负责人协调工作。负责人可重试、说明延期或在授权范围内取消；同一异常不会无限创建协调任务。已用尝试次数、每日预算和原始承诺不会因重新规划而清零。协调本身受阻时明确显示需要处理。

内置技能按版本记录派收、验收和岗位要求，随本次固定输入交给成员。技能目录显示适用岗位与版本，正文不会获得执行权限。

## 3. 项目工作台

- 左侧：项目、团队、历史与搜索；显示待确认数和阻碍，兼容旧任务路由。
- 中间：默认与负责人对话，阶段活动可展开；失败、退回与待处理持续可见。消息引用同一工作项与成果身份。
- 右侧：实际整稿、图片、版本变化、依据和审稿意见；在当前项目内退回或请求原生批准。
- 成果按钮打开明确版本；搜索定位项目中的消息、工作或稿件；界面刷新与重连从权威状态恢复，不重复启动工作。
- 设置、成员模型配置、工具连接与技术诊断按需打开。首个业务模块仍是单账号图文，未配置的发布能力明确标示条件。

## 4. 实施分工与顺序

1. **协作主干（根代理）**：`server/business-handoffs.mjs`、`business-work.mjs`、`business-scheduler.mjs`、`business-collaboration.mjs`、`business-protocol.mjs`、`business-api.mjs`、`projects.mjs`；新增版本化业务技能。验证收件、过期结果、依赖释放、退回和负责人异常处理。
2. **界面（business_ui）**：`ui/**`、`tests/business-ui-state.test.mjs`。实现统一项目工作台和精确成果预览，保留旧操作入口与原生批准。
3. **数据与恢复（business_data）**：Store、BusinessStore、进程证明、执行调度、项目上下文、成果版本及相关数据/恢复测试。根 PID 消失不能证明进程树退出，未经确认不得释放运行资格。
4. **接入与旅程（publishing_runtime）**：`tools/mcp.mjs`、`tools/team.mjs`、业务 fixture 与运行测试、原有桌面/发布边界。补受控业务接口，验证目标到交付和返工全过程；不暴露发布批准。
5. **集成（根代理）**：核对类型/接口、审查代理改动、完成失败分支验证，更新使用说明与实际验证记录。

## 5. 验收

- 必须覆盖：成员声称完成却没有文件；收件但未核验时下游不能开工；旧收件结果被拒绝；退回形成新版本；失败持续留在未完清单并进入负责人处理；重复回报不重复派工；预算和停止规则不被绕过。
- 真实本地子进程 fixture 走通规划、并行制作、接收、独立审稿、退回、重交；明确它只证明本地控制流程，不冒充真实模型或平台验收。
- Electron 可信模板实际渲染中文图文；桌面/浏览器检查统一界面的创建、对话、查阅整稿和退回旅程。
- 交付前运行 `npm test`、`npm run check`、`npm run build`。
- 官方模型实际生成、平台账号登录、真实发文与回读均单独记录范围。没有实际证据的门禁写为未验证；不能以测试通过覆盖。

自动发布、排期与指标的既有代码保留兼容，本轮优先把完整的团队协作与成果审阅流程做实，再依据真实接入证据开放后续能力。

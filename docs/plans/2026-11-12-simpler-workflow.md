# 更简单的工作流程 Implementation Plan

**Goal:** 将 CLI Team 的日常操作收敛为“交代目标 → 团队推进 → 看成果与提修改”，减少重复入口和配置往返。

**Architecture:** 沿用现有项目、任务、草稿、成员权限与验收服务。前端统一新工作入口，通过明确的路由上下文返回未完成的创建或稿件；使用已有机器证据与项目状态生成下一步提示，完整过程按需展开。

**Tech Stack:** Node.js 24、React 19、TypeScript、Express、SQLite、Electron，使用现有 Playwright 进行隔离浏览器验证。

---

## 已确认的范围

- 一个“开始新工作”入口，按实际用途选择“完成一次任务”或“持续运营内容”。手工选执行方式保留在高级工具。
- 建项目缺少成员时保留草稿，配置后可直接继续；新项目继承保存的完整默认团队，不自动选中无关成员。
- 从稿件进入账号或项目设置时携带项目、稿件和版本，配置后返回原处。不存在的项目不能默默切换到另一项目。
- 默认以会话和一句真实进展为中心；成果与完整交接过程按需打开。受阻信息继续可见，并提供具体下一步。
- “等待审稿”和“可以确认发布”分开。账号登录、检测、绑定按实际状态逐步呈现；调整排期后直接显示返回的新版本。
- 机器检查、独立审稿、权限范围与桌面发布确认保持有效。绑定账号使旧检查失效时继续明确显示重新审查；结果未知不重发。

## 实施与文件分工

### 1. 统一入口与往返路径（主代理）

- `ui/App.tsx`、`ui/StartWorkDialog.tsx`、独立入口样式。
- `ui/workbench/navigation/WorkbenchNav.tsx`、`useWorkbenchRoute.ts`：清除重复导航，支持受约束的继续位置。
- `ui/projects/BusinessWorkspace.tsx`：创建状态和设置上下文接到路由，成果按需打开。
- `ui/projects/ProjectCreateDialog.tsx`：沿用默认团队完整名单并支持配置后的草稿恢复。
- 已停用或缺失的默认成员继续显示，可明确移除；默认团队缺少审稿时，只在已授权名单内推荐。
- 新建弹窗和按需成果面板关闭后恢复可用焦点，配置页与新弹窗拥有焦点时不抢回。
- 对路由刷新、非法返回参数和成员授权默认值增加针对性测试。

### 2. 每日进展与按需查看（界面代理）

- `ui/projects/ProjectCommandStrip.tsx`、`ProjectConversation.tsx`、`ProjectSidebar.tsx`、`ProjectHome.tsx`。
- `ui/projects/team-workspace.css`、`team-communications.css`。
- 将内部交接计数折叠，保留受阻摘要与定位；成员接收人默认不占据普通消息输入区。
- 状态表达区分运行、排队、暂停、失败、需要用户处理；不把“已建立”当作“正在执行”。

### 3. 成果下一步与配置上下文（业务界面代理）

- `ui/projects/businessState.ts` 与相关纯状态测试。
- `ui/content/ContentWorkbench.tsx`、`content-workbench.css`。
- `ui/projects/BusinessSettings.tsx`、该组件独立样式。
- 依据当前固定版本的检查和审稿显示状态，给缺少条件的主要处理入口；细节按需展开。
- 配置页接受指定项目与目标区域，自动检测不替代账号确认，不自动恢复整个工作区。
- 未保存的项目设置保留在原项目中，服务端归档或移除项目也不静默丢弃编辑；提交前重新核对版本。

### 4. 验证与交付（验证代理、主代理）

- 更新 `tools/smoke-business-ui.mjs`，新增针对流程往返的隔离场景；使用真实 loopback 服务、浏览器与本地演练数据。
- 覆盖：两种新工作入口、创建草稿经过成员配置返回、B 项目进入设置仍是 B、回到原稿件、过程展开、真实受阻提示、旧版不能批准、窄屏焦点和无横向溢出。
- 运行 `npm test`、`npm run check`、`npm run build`；失败修复后只重复相关检查。
- 更新实际截图和说明，重新打包桌面、验证成品与项目快捷方式；正常提交推送并核对远端提交。

## 验收标准

1. 新用户无需理解派工模式即可开始；配置中断后不用重新找目标或重填。
2. 常用页面始终说清当前状态、下一步和处理对象；没有操作时不会伪造忙碌。
3. 从多个项目的任一稿件前往设置，项目身份和返回版本不会丢失。
4. 未完成机器检查或独立审稿的稿件不会被称为“可以批准”；所有原发布门禁继续生效。
5. 草稿、深链接、键盘操作、窄屏和现有任务访问经过实际验证。

本轮由用户“优化吧”授权在当前工作区实施。各代理按文件分工协作，验证材料保存在忽略的 `work/` 中。

# 负责人调度

用户选择任务负责人及 1–4 名可调度成员。负责人先只读检查需求和材料，输出最多 6 个有依赖关系的步骤，按成员技能指定执行者。服务端验证结构、成员授权、唯一步骤标识和依赖无环，随后在原任务目录按依赖串行执行。负责人最后检查真实文件并集成成果，之后才执行原有机器验收、独立评审和用户接受流程。

选择此方案是为了复用现有产物与验收版本绑定，避免新增文件合并器在多个独立目录之间覆盖成果。任务内写入串行；不同任务仍遵守全局并发配置。它不是操作系统沙箱，成员只能在已授权目录和权限内工作。

执行模式 `direct` 保留既有行为，`delegated` 将 `assigneeId` 用作负责人，`participantIds` 限定成员池。负责人需具备编辑权限以集成成果，规划阶段强制降为只读。独立评审者不得同时属于负责人或协作成员池。

步骤信息保存在任务的 `coordination` 中，每个步骤关联实际运行 ID。负责人计划绑定规划运行 ID，结果只能推进对应轮次。普通成员返回额外派工字段不会继续派工。计划错误直接阻塞；普通步骤失败、机器验收失败或评审要求修改会带着反馈回到负责人重新规划，受已有 `repairLimit` 限制。权限或输入完整性错误停止自动返工。

取消、服务重启和阻塞同步停止步骤状态；重启不自动重放。既有文件保留，继续任务时重新规划剩余工作。已启动的协作任务暂不支持改派负责人和更换成员池。

界面展示模式、成员技能、计划、步骤依赖、执行人和结果。成员完成只是未经整体验收的结果；最终是否接受仍由原门禁和人工确认决定。CLI 和 MCP 使用同一数据结构。

验收覆盖：结构化报告兼容旧客户端、非法计划拒绝、依赖与授权校验、只读规划、成员结果汇总、有限返工、取消与重启、真实受控 Node CLI 和机器验收链路，以及浏览器操作。真实模型联网执行另行区分，不能由替身测试推断通过。

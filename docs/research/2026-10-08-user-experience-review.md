# CLI Team 使用体验研究

日期：2026-10-08。对象：Windows Electron 桌面端。

下一轮的目标应当很具体：用户交代目标、材料和完成标准后，可以放心去做别的事；回来能看懂当前进展、处理需要自己决定的问题，并根据实际成果作出验收判断。

当前最值得投入的顺序是：**修复表单裁切和草稿丢失 → 理顺启动准备 → 集中待处理事项 → 改善成果验收 → 说明恢复范围 → 完善多任务与复用。**

## 研究范围与证据

本轮新增研究文档、隔离探针和截图，没有修改产品源码。已有的技能描述、负责人派工、同伴咨询、人工答复、检查点复用、失败诊断和停稳后改派，都作为现有能力使用。

证据分为三类：

| 类型 | 本轮做了什么 | 能支持的结论 |
| --- | --- | --- |
| Electron 界面实测 | 运行现有构建、真实 preload 与 BackendHost；使用独立工作区和固定 Node 执行器，脚本驱动真实界面 | 窗口尺寸、控件布局、输入值变化、查看日志后的返回行为 |
| 源码与样式审查 | 核查新建、成员选择、材料锁定、看板、任务详情、验收和桌面生命周期 | 实际入口、状态依赖和当前实现的缺口；没有冒充全部已操作复现 |
| 官方资料核验 | 读取 Linear、GitHub Desktop、Claude Code、Superset 和 WCAG 官方资料 | 可借鉴的交互及适用边界；没有运行这些产品 |

界面探针使用 Electron 44.7.0，窗口外框 1040×700、内容区 1024×661、DPR 1，与产品允许的最小窗口尺寸一致。研究入口创建隐藏的 BrowserWindow，运行现有桌面渲染内容与后端，未运行产品的 `desktop/main.mjs` 入口；没有覆盖成品安装、系统通知、真实用户操作耗时或不同 Windows 缩放设置。测试任务仅在独立目录创建，真实模型调用为 0；探针结束后后端退出、工作区锁释放。

本轮尚未开展用户访谈。下文的“10 秒”“一次点击”等均为建议验收目标，不是已测得的效率提升。

原始截图、测量数据和研究笔记保留在本地隔离工作区，未随源码仓库发布。

## 1. 优先修复：能操作到底，输入不能丢

**已实测的布局缺陷。** 在 1040×700 窗口下，新建协作任务弹窗的底部字段和“确认创建任务”按钮被裁切。外层弹窗约 562px 高，内容约 928px；内部正文约 817px 高却没有可滚动空间。脚本设置正文 `.modal-body.scrollTop` 至底部后，控件位置没有变化，确认按钮仍不可见；本轮未验证真人滚轮、Tab 或放大窗口等替代操作路径。

**已实测的输入损失。** 填写 1790 字目标后，通过 Escape 或关闭按钮离开，再点新建，目标均变成 0 字。另一个固定协作任务中，未保存的答复在“查看负责人处理日志 → 返回任务”后清空。

验收备注与返工意见还存在同类风险：切换弹窗会清理对应状态；这一点来自源码审查，本轮未逐项界面复现。

建议先修正表单容器高度与滚动关系，保持底部操作可达；再统一保护新任务、答复、返工与验收文本草稿。用户可以继续未写完的任务，明确放弃才清空。查看日志或文件后，应回到原任务、原位置和原输入。

草稿按工作区、任务、计划和问题区分。旧计划的文字可保留供复制，不自动提交到新问题；恢复文字不恢复“接受缺失验证”等授权勾选，也不启动任务。成功提交后只清除相应草稿。

**建议验收：** 在产品允许的最小窗口与 100% / 125% / 150% 缩放场景下，所有表单字段和主操作均可访问；三类任务内草稿各输入 200 字，两次查看日志或成果后逐字保留；重启可恢复未提交任务草稿；不同任务互不串入。上述缩放场景尚未验证。

## 2. 启动前把材料、成员与完成标准准备好

现在新建表单能勾选“创建后立即启动”，材料却只能创建后进入详情添加，而第一次运行后材料锁定。用户想交给团队处理现成资料，很容易按错顺序。

建议把新建流程整理为“描述目标 → 选团队、材料与完成标准 → 保存待办 / 开始执行”。可在同一页面分区完成，无须增加机械的逐步确认。选了材料就先导入成功，再启动；没有材料可直接跳过。启动前用一句话说明材料将固定，以及此次任务实际使用的工作目录。

同时降低两处配置成本：

- 新建和改派共用成员可用性判断。当前新建只过滤启用状态，缺失 CLI 入口的成员仍可选；改派已有更完整判断。缺失成员应禁选并给出就地修复入口。“本机检测到客户端”继续与“登录和模型可用”区分。
- 常用配置只展示名称、角色、擅长内容和必要模型选择，把路径、参数数组、输入模式放入高级配置。完成标准先允许自然语言人工核对；需要自动检查时，用“程序 + 参数”控件与明确预设代替只给 JSON 输入，底层仍使用参数数组。

这些是源码确认的流程问题，材料启动冲突与不可用成员没有在本轮探针中逐项运行复现。

**建议验收：** 两份材料中一份上传失败时不会先启动；重试成功后一次明确操作即可开始。缺失成员不能被默认选中或提交。非开发用户不写 JSON 也能设定完成标准；未配置自动检查时一直明确显示没有机器证据。

## 3. 打开程序先看见“需要我处理”

当前首页默认进入团队讨论；看板只按任务状态分列，任务内问题和对应操作散在多个区块。用户需要自己判断哪些事件现在仍然有效、哪些只是历史。

建议增加跨频道的“需要我处理”，每项显示：任务名、当前原因、等待多久、一个直接动作。任务顶部复用同一信息，避免两个地方给出不同结论。

| 当前事实 | 用户看到的说明与动作 |
| --- | --- |
| 负责人正在咨询同伴 | 团队内部处理中；留在进展中，通常无需用户答复 |
| 当前问题需要人工补充 | “需要你补充接口字段” → 打开对应问题 |
| 答复已保存，尚未继续 | “答复已保存，等待继续” → 查看恢复范围并继续 |
| 用户主动暂停 | “你已暂停” → 按需继续，避免显示为新故障 |
| 当前执行或检查失败 | 展示当前原因 → 对应文件、成员配置或诊断入口 |
| 已完成执行，等待人工验收 | “待你验收” → 打开成果与验收依据 |

“已读”“稍后处理”和“问题解决”分别处理。历史失败在任务继续成功后退出当前待处理列表，仍保留在时间线。状态依据当前计划、运行、问题和验收事实，不能根据成员的一句自述判断解决。

**建议验收：** 20 个任务的固定场景中，不必逐个打开详情，就能识别所有必须本人处理的事项；进入程序 10 秒内能说出下一步该做什么；当前问题到答复或诊断位置不超过一次点击；保存答复不会被误读为已经恢复执行。

## 4. 围绕成果验收，让用户读得懂、找得到依据

目前看板把实际等待用户验收的状态写成“待评审”；任务详情列出评审人，却没有集中呈现独立评审结论。机器检查区主要显示命令、摘要和退出码；普通用户仍需翻找事实。

文件阅读也影响决策：任务产物只显示文件名，两个 `index.ts` 难以区分；`.mjs/.ts/.tsx/.py/.css` 目前不能直接预览。任务工作目录和单个文件的位置缺少直接入口。

建议任务详情使用桌面分栏或全页视图：顶部展示当前状态与动作，中间优先呈现成果和文件清单，旁边放本次验收依据，日志按需展开。先完成常见代码的纯文本预览、相对路径、行号、查找和文件切换，再考虑更复杂的差异视图。预览不执行交付脚本或 HTML。

决策附近明确分开以下内容：

- **交付内容：** 当前文件、所属步骤和版本；成员总结只是阅读提示。
- **机器验证：** 实际检查结果、测试数与跳过数、是否覆盖当前版本；未知、缺失和失效分别显示。
- **独立评审：** 本次结论与证据；未配置、未运行不能显示成通过。
- **用户完成标准：** 对应成果或证据入口；有关联文件不等于业务已经通过。
- **用户决定：** 接受当前结果或提出修改，反馈绑定文件、片段与版本。

**建议验收：** 不读原始日志即可看清本次成果、机器证据、独立评审及未证明项；同名文件可辨认，常见代码可安全阅读；失效机器检查继续阻止验收；对旧版本的反馈在文件变化后有明确标记。

## 5. 点“继续”前，说明保留与重做范围

局部恢复已经实现。下一步应把用户最关心的影响讲清楚，例如：“保留需求分析与接口设计；重新执行页面实现，因为交付文件已变化；之后重新验证。”

这段预告应由实际恢复判定产生。用户补充新要求时，立即说明是否转为重新规划；等待期间文件或计划变化，执行时重新核对并显示差异。用户无需学习内部检查点术语，也不用每次为了普通恢复再经过一轮确认弹窗。

现有检查点验证有效成果与依赖，不能把它称为文件快照或“还原到这一刻”。预览也不承诺各 CLI 的会话、外部副作用或源文件会一并回退。

**建议验收：** 三步任务前两步完成、第三步失败时，用户在执行前能准确预测保留与重做项；实际恢复与预告一致。修改前序交付或新增要求时，相关依赖重做的原因可见。

## 6. 支持多任务和离开前台的使用方式

最小窗口实测中，看板可见宽度为 802px，六列内容为 1380px，需要横向滚动。没有发生整个页面横向溢出，但不便同时观察全部状态。任务卡还缺实际执行者、当前步骤与筛选入口。

建议增加紧凑列表，支持按任务名、频道、成员和需处理状态筛选。每行显示负责人、当前执行者、步骤、等待原因与更新时间；沿用真实宿主状态，不显示推测的百分比、费用或完成时间。保留用户上次选中的任务与过滤条件。

桌面可增加可选的关闭到托盘，以及需要人工答复、当前失败、待验收时的系统通知。正常成员报告留在任务进展中，避免每段输出都提醒。点击通知直达相关任务；同一问题在重连后不重复提醒。现有“停止任务并退出”的清理行为继续明确可用。

**建议验收：** 固定多任务场景下无需逐个详情核对谁在工作；切回应用保持原上下文；同一需要处理事件只提醒一次；关闭到托盘与停止退出的实际行为符合文案。通知和托盘属于建议新增能力，本轮未实现或实测。

## 7. 熟练之后，减少每次从头配置

先做“从此任务复制为待办”，沿用团队、角色、擅长描述对应的选择、要求和检查设置。材料由用户明确选择复用哪些副本；新任务使用新 ID、保持未启动，不复制历史运行、通过结果或验收状态。缺失成员在保存前提示替换。

后续再提供轻量团队模板，以及基于已有技能描述的成员推荐理由。例如“这项任务需要数据库分析，因此建议给熟悉 SQL 的成员”。手填能力、实际执行记录和模型建议应可区分，推荐不会自动提升权限。

**建议验收：** 第二个同类任务只需选择原配置、填写新目标并确认材料，即可生成独立待办；原任务和文件保持不变；成员与检查配置仍可逐项修改。

## 可读性与一致性应随每批一起改

当前正文基础字号为 13px，部分说明更小；`--text-muted: #82919e` 对白色背景的计算对比度约 3.23:1，对 `#f4f6f7` 约 2.98:1。用于普通重要说明文字时低于 WCAG AA 常规文字的 4.5:1 要求；禁用控件、装饰元素等不能混作同一判定。[WCAG 官方说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

建议把常规阅读文字提高至约 14px，提升重要说明的对比度，并提供紧凑密度选择。任务详情现在宽度上限 780px，内容长，适合逐步移入桌面全页或分栏；第一批先修复滚动，不必等待整体布局改版。

已有弹窗语义与焦点约束，不需要重新声称“增加键盘支持”。需要补验的是各表单的完整键盘路径、返回后的焦点、草稿保护，以及 125% / 150% 下的可访问性。术语统一用“负责人”“当前执行者”“待你验收”“自动检查”，CLI 参数与底层标识留在高级信息中。

## 建议实施批次

| 批次 | 交付范围 | 用户可直接感觉到的变化 | 检查重点 |
| --- | --- | --- | --- |
| 第一批：基础可靠 | 新建表单滚动、所有输入草稿保护、成员可用性一致、材料先于启动 | 写的内容不会随跳转丢失，小窗口也能创建任务，启动前配齐资料 | 最小窗口、输入往返与重启、部分上传失败、缺失成员 |
| 第二批：看懂与判断 | 需要我处理、任务顶部主操作、成果及验收依据、恢复范围预告 | 一眼知道该处理什么、凭什么接受、继续后会做什么 | 当前与历史状态、版本变化、证据缺失、恢复预告一致性 |
| 第三批：持续使用效率 | 多任务列表与筛选、通知与可选托盘、任务复制、配置简化 | 能放心离开前台，重复工作不必重复配置 | 通知去重、停止退出、上下文保持、新旧任务隔离 |

每批选择能体现真实使用问题的固定场景验证。桌面布局、用户操作路径、真实模型协作效果分别记录；自动测试通过不替代人工可用性评估。

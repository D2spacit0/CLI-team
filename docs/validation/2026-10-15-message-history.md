# 2026-10-15 聊天历史与连续阅读优化

按用户要求继续优化源码和开发构建，本轮未打包。开发与桌面检查使用项目内的独立测试目录，没有启动原工作区服务或操作原任务。

## 用户可见的改进

| 原来的问题 | 现在的行为 |
| --- | --- |
| 只能看到最近 100 条，无法继续查看旧记录 | 默认加载最近 100 条，顶部可逐页加载更早消息 |
| 刷新替换最近记录，正在读的旧消息会离开列表 | 保留已经展开的历史，新消息追加到后面 |
| 断线期间新增超过一页的消息可能被截掉 | 从上次读到的位置分批补齐，不跨过中间记录 |
| 历史页插入、错误提示消失后正文位置变化 | 按正在阅读的消息正文和位置恢复；历史翻页不增加新消息计数 |
| 切换房间时旧请求和新页面相互干扰 | 每个房间独立保存读取状态，迟到响应仅更新对应房间 |
| 加载失败后不便继续 | 首次读取、刷新和历史翻页都可重试，已读内容保留 |
| 缓存历史可能残留已归档任务消息 | 归档或恢复后重新核对已展开范围，旧消息恢复不计为新消息 |
| 矮窗口中任务摘要挤占正文，发送按钮边缘被裁切 | 压缩摘要及间距，保留完整计划入口、可读正文和完整发送按钮 |

阅读历史时可随时点击“回到最新”。同一窗口缓存最近访问房间的历史；重开应用从最近记录开始。缓存有容量上限，不承诺无限保留所有房间的已展开页面。

## 读取性能

原实现会读取并反序列化全部房间的消息，再筛选当前房间；新实现使用 SQLite 房间索引，先过滤可见记录，再读取指定页。消息按数据库写入顺序分页，不依赖客户端时间戳。

本机 Node.js 24.12.0，以 20 个房间、共 20,000 条合成消息读取同一房间的最近 100 条，预热后交替执行 9 轮：

| 读取方式 | 中位耗时 |
| --- | ---: |
| 原来的全量读取与筛选 | 209.59 ms |
| 房间索引分页 | 1.18 ms |

两种方式返回的消息 ID 完全相同。[测试数据与逐轮耗时](../../work/message-history-20261015/benchmark.json)保留可复查结果；这是本机合成数据的测量，不代表所有真实工作区的固定耗时或整体界面速度。

## 实现与边界

保留 `/api/rooms/:id/messages` 的数组响应。新增 `/api/rooms/:id/messages/page`，默认 100 条、上限 200 条；`before` 与 `after` 不能同时使用，游标必须属于当前房间。每页带写入顺序和归档可见范围标识，界面据此串行补读或重新核对历史。已有数据库只新增消息索引，旧记录内容和写入顺序保持不变。

消息读取从 App 抽为按工作区、房间管理的状态，房间缓存上限为 8 个；持续事件采用定时合并刷新，避免一直等待事件停止才显示新内容。已读取的每页仍使用原有消息卡片，不增加新的依赖。

本轮桌面场景中的 DSH 握手使用本地固定协议程序，真实模型调用为 0。没有重新验证真实供应商服务或多模型协作质量，也没有执行成品打包和成品回归。

任务操作回归运行 6 个预先登记的本地固定文件作业；两组桌面检查均确认退出前草稿保存、后台进程退出和工作目录锁释放。其余专项桌面场景本轮未重新运行。

## 复现与保留记录

[修改前复现](../../work/message-history-20261015/before-reproduction.json)确认存入 230 条只能返回 100 条，且会扫描全体消息。修改前源码位于 work/message-history-20261015/before/。

首次桌面检查暴露了重试时错误提示清除导致的正文移动。现保留翻页开始时的正文锚点，并在用户中途滚动时更新它。测试也改为比较原消息正文的位置；插入历史后，第一条可见消息可能变成补入的前一条，不能将这种变化误判为阅读位置丢失。

原键盘脚本仅发送 keyDown/keyUp，未触发按钮的 Enter 默认操作；补齐 char 事件后通过。后续截图发现矮窗口正文空间不足，最终检查增加了正文可见高度与发送按钮完整性断言。最初失败日志保留在同一工作目录，没有当作通过记录。

最终源码、构建资源、发布入口哈希与检查回执汇总在[机器记录](../../work/message-history-20261015/validation-results.json)。没有执行 package:desktop 或 dist:desktop；现有快捷方式和发布目录保持原样。通过项目目录的 npm start 可使用本轮源码与开发构建。
